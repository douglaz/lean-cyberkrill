# lean-cyberkrill: plan for a Lean 4 port of cyberkrill (v1)

Goal: grow the Lean 4 ecosystem with reusable Bitcoin, Lightning and Fedimint libraries, and ship the
cyberkrill CLI on top of them. Reference implementation: `github.com/douglaz/cyberkrill` @ `27cad1f`
(read-only; all `file:line` references below are at that commit).

Status: approved by the owner on 2026-10-19, with all eight defaults in section 6 (default #4 as
amended there). Phase 0 bootstrapped this repository.

## 1. Decisions

| Topic | Decision |
|---|---|
| v1 scope | Offline libraries and commands **plus** the network commands (Bitcoin Core RPC, price feeds, LNURL-pay, Fedimint config fetch, DCA report). |
| Out of v1 | Hardware wallets (Coldcard, Trezor, Jade, Tapsigner, Satscard); BDK (Electrum, Esplora, BDK bitcoind backend, BDK coin selection). |
| MCP server | Never ported. |
| Proof level | **M**: published test vectors for every library; proofs of encode/decode round-trips, of checksums catching what their spec says they catch, and of exact BTC/sats/msats conversions. No verified crypto. |
| HTTPS | Our own ~100-line C wrapper over libcurl (OpenSSL backend) behind a small Lean interface that Lean core's HTTP client can replace later. Bitcoin Core RPC uses it too. |
| Curve ops | libsecp256k1 (nixpkgs 0.8.0, recovery module on) for verify, recover and sign, behind one small Lean interface so a verified implementation can replace it after v1. |
| SHA-256 | Copied from `pure-algebra/lean4-hash` @ `ab7eda4` (v4.33.1, MIT; `sha256_spec` proven against FIPS 180-4), ported to v4.35.0, attributed, spec reviewed. |
| RIPEMD-160 | Our own, about 130 lines in `bitcoin` under the dual licence, with HASH160 = RIPEMD-160(SHA-256), tested against the 9 test messages on the RIPEMD-160 authors' page, with expected digests generated by nix `openssl dgst -ripemd160` (the page states no licence, so it is cited, not copied). Owner decision, 2026-10-19. |
| C code | Only in the `secp256k1` and `http-curl` packages. |
| lean-miniscript | Copy a narrow subset of `febyeji/lean-miniscript` @ `cb9bc5f` (v4.32.0, MIT) and own it: `LeanMiniscript/Psbt/Codec.lean`, `Psbt/Fields.lean` and their dependencies (tx, serialization, script syntax, base64), about 1,400 lines, plus tests and the BIP174/370/371 vectors. | Layout | One repo, `douglaz/lean-cyberkrill`, several Lake packages in subdirectories, one nix flake and toolchain. At v1, decide package by package whether to split one out. |
| Visibility | Public since 2026-10-22 (owner decision; this replaces the original "private until v1"). Repo creation, pushes and Reservoir publication need the owner's go-ahead. Standing go-ahead (owner, 2026-10-19): feature branches may be pushed and PRs opened; the owner merges. |
| Toolchain | Lean v4.35.0, packaged by this repo's flake (nixpkgs `lean4` is 4.34.1 at the pinned `fe13242`; lean4-nix stops at 4.34.0). Dynamic glibc build until v1; static musl only for the v1 release. |

Fixtures come from a published test mnemonic; the fixture at `frozenkrill.rs:243` is not copied. |
| Licence | Dual **MIT OR Apache-2.0**, as cyberkrill. Detection details in section 5. |
| Tracker and runs | beads (`br`) tracker; work runs in work sessions on feature branches; the owner merges PRs. |

## 2. Packages and dependency order

```
sha256 ──► bitcoin ──► lightning
                  └──► fedimint-invite
secp256k1 (FFI)      http-curl (FFI)        (no Lean deps; nothing pure imports them)
all six ──► cyberkrill (app)
```

Pure packages never import an FFI package. Curve operations that pure code needs (the PSBT pubkey
checks, BOLT11 recovery, verification and signing) arrive as a supplied capability (a structure of functions) that the
app fills from `secp256k1`. Proofs needing Mathlib, if any, go in a separate `<pkg>-proofs` package so
the libraries stay Mathlib-free.

## 3. Outstanding facts each phase must honour

- **Full Core RPC list.** `listunspent`, `scantxoutset`, `getdescriptorinfo`, `deriveaddresses`,
  `createpsbt`, `walletcreatefundedpsbt`, plus five that were missing from the first list:
  `importdescriptors` (`bitcoin_rpc.rs:764`), `getblockchaininfo` (`:725`), `getreceivedbyaddress`
  (`:1172`), `getrawtransaction` (`:1310`), `getblock` (`dca_report.rs:204`, DCA report only).
  `list_unspent_for_descriptor` imports the descriptor into the node's wallet and ignores errors
  (`bitcoin_rpc.rs:774`). Keep that behaviour and document it.
- **Local weight and fee estimation.** `onchain-create-psbt` and `onchain-move-utxos` compute fees
  locally. The estimate assumes every input is `P2WPKH_MAX` and every output script is 22 bytes
  (`bitcoin_rpc.rs:982-993`), rounded up to vbytes as in `calculate_fee_with_feerate` (`:997`). Port it
  exactly. `move_utxos` selects inputs locally, largest first, when `--max-amount` is set (`:1329-1345`).
  Only `onchain-create-funded-psbt` leaves coin selection to Core. The port keeps that selection, but its
  single output is the full selected total minus the fee, with no clamp to `--max-amount`. cyberkrill's
  Core path clamps the total (`:1354`) and so pays any excess to the miner (`:1390`, `:1401`); its BDK
  path spends the whole selection. Owner decision, 2026-10-19: a documented, tested delta, reported
  upstream as douglaz/cyberkrill#152.
- **Exact amounts vs `f64`.** cyberkrill sorts and sums BTC as `f64` (`bitcoin_rpc.rs:1330-1345`), and
  `onchain-decode-psbt` prints `value_btc` from `f64` (`main.rs` `decode_psbt`, from `:2293`). The port
  parses Core's JSON numbers exactly and uses msat `Amount` throughout. Golden tests compare parsed
  JSON values, not bytes, and any edge-case difference from cyberkrill is listed in the README.
- **BIP370 v2 PSBTs.** cyberkrill's rust-bitcoin 0.32.8 rejects PSBT version > 0, but the port's
  `onchain-decode-psbt` decodes v2 (owner decision, 2026-10-19). This and the `move-utxos` output above
  are documented, tested exceptions to golden parity, the BOLT11 signing hash below is a third, and
  three BIP rules the PSBT decoder keeps where rust-bitcoin 0.32.8 is laxer are a fourth (owner
  decision, 2026-10-23: canonical CompactSize key types, the global xpub path length matching its
  depth, and no v2-only fields in a v0 PSBT; on 16 such inputs cyberkrill exits 0 in the pinned
  offline `onchain-decode-psbt` capture while the port's decoder rejects all 16; the capture and
  tests are recorded in Phase 4a's PSBT field-parity follow-up); otherwise the port exits non-zero
  wherever cyberkrill does.
  Goldens cover v0; v2 gets its own tests from the BIP370 vectors; the README lists each delta.
- **BOLT11 signing hash.** The port hashes the invoice's own lower-cased hrp and its data part as
  written (BOLT #11 L117-119; owner decision, 2026-10-21), as LND and Core Lightning do.
  cyberkrill's lightning-invoice 0.34.0 hashes a re-encoding of the parsed fields (`de.rs:395`,
  `lib.rs:1084-1120`). The two agree on canonical invoices and on every spec example that decodes,
  and differ on the non-canonical encodings the crate accepts: padding that is not canonical (non-zero
  padding bits, or a whole extra padding symbol) in a byte-valued field it decodes, leading zero
  symbols in `x`, `c` or `9`, and an hrp amount with leading zeros. The port rejects the first two,
  each with a named error (owner decision, 2026-10-21: BOLT #11 L208's writer MUST, L239-241's reader
  SHOULD, as Core Lightning mostly does), so there it exits non-zero where cyberkrill decodes. Fields
  both keep raw (unknown tags, an `f` above version 18, a wrong-length `p`/`s`/`h`/`n`, whose L214
  rule is its own deferred owner decision) are hashed as written by both and get no padding check.
  The port accepts a leading-zero amount, as cyberkrill does; on such an invoice the two recover
  different payee keys (no `n` field), or only one of them verifies (a valid `n`). Both are this
  third documented, tested exception to golden parity: Phase 5 tests the rejected classes as negative
  vectors and the leading-zero amount as positive ones, Phase 7b captures cyberkrill's output on
  each, and the README lists it.
- **Hybrid public keys.** rust-bitcoin 0.32.8's `PublicKey::from_slice` rejects a 65-byte hybrid key
  (prefix 06/07), but cyberkrill parses two v1 inputs with libsecp256k1's own `ec_pubkey_parse`,
  which accepts one whose prefix matches y's parity: PSBT `bip32_derivation` keys (input and output
  maps) and `ln-encode-invoice`'s JSON `destination` and `routes[][].src_node_id`. The port follows
  cyberkrill on both (owner decision, 2026-10-21): `secp256k1` adds `compressPubkey`, that rule
  returning the 33-byte compressed key, and the `bitcoin` capability carries it beside the strict
  `isValidPubkey`, which still checks `partial_sigs` keys, signatures and descriptors. The PSBT codec
  keeps each key's raw bytes, where rust-bitcoin rewrites bip32 keys to 33-byte compressed (no v1
  command shows the rewrite), and `Psbt.checkBip32SamePoint`, which the app runs on every PSBT it
  parses, rejects two encodings of one point in one bip32 map, as rust-bitcoin does. So this is no
  delta: the port exits non-zero wherever cyberkrill does, and the README notes the raw-bytes choice.
- **BDK route on `--descriptor` + `--bitcoin-dir`.** cyberkrill sends that combination to BDK on
  `onchain-list-utxos` (`main.rs:1506-1508`) and on the three PSBT commands (`:1628-1630`, `:1738-1740`,
  `:1871-1873`). v1 rejects it with a clear message (section 6) and does not quietly run Core.
- **Exactly one OpenSSL.** Lean 4.35 only puts OpenSSL on the link line; its runtime hooks are stubs,
  and the flags depend on Lean's build configuration (`src/CMakeLists.txt` L416-425 @ v4.35.0). The
  toolchain links OpenSSL 3.6.0; nix curl 8.22.0 links OpenSSL 3.5.8. The final executable must contain exactly one
  OpenSSL: build curl against the toolchain's OpenSSL or the reverse, settled in Phase 1.
- **Lake linking.** Lake v4.35 deprecates `extern_lib`. Use a custom target with
  `moreLinkObjs`/`moreLinkLibs` (Lake README @ v4.35.0). An executable gets its dependencies' link objects and
  libraries, but only the root package's raw link flags (`recComputeModuleLinkInfo`,
  `Lake/Build/Module.lean` L1299-1337, root `linkArgs` at L1334-1336; `Build/Executable.lean` L20-29),
  so each FFI package ships its own link targets.
- **CA bundle.** See `http-curl` above. A nix-built binary otherwise finds no CA bundle on non-NixOS
  hosts.
- **Price feeds.** `cyberkrill-core/src/price_feed.rs` has nine feed URLs (Coinbase, CoinGecko,
  Kraken, Bitstamp, Gemini, CEX.io, Yadio, blockchain.info, Fedi), but `convert-amount --help` says
  "median of 5". Check which is right in Phase 9 and match the code's behaviour.
- **Entropy.** `generate-mnemonic` uses `rand::rng()` (`main.rs:2651-2669`). Verify that Lean 4.35's
  `IO.getRandomBytes` draws from the OS CSPRNG before using it; otherwise read `getrandom` through a
  C call in `secp256k1`.
- **SLIP-132 has no v1 caller.** Its only caller is `trezor.rs:12,196` (out of v1). The scope lists it,
  so see section 6.
- **Static musl release task (Phase 10).** Known to work: source-build the Lean 4.35 toolchain against
  musl (~36 min, no patches; prefetch mimalloc, cadical and leantar; turn the baked-in `.so` paths into
  `-l` flags) plus a `LEAN_CC` wrapper ending in `-Wl,-Bstatic`. The probe recipe is committed under
  `nix/musl/` in Phase 0. Mixing the official glibc runtime with musl also links, but it is not shipped.
- **Safety.** Tests use only published vectors, published test mnemonics, the BOLT #11
  specification's published example private key (tests only), recordings from a throwaway regtest
  node, and synthetic or script-generated fixtures under the third-party rule (for example
  cyberkrill's captured outputs on those inputs, synthetic provider responses, our own LNURL and LUD
  JSON, values a committed script derives from published inputs). Never anything from the owner's
  node, wallets or devices. Tests never reach the internet, port 8332 or `~/.bitcoin`. Nothing
  committed contains private keys, seeds, xprvs, tprvs or WIF keys, or real addresses, xpubs or
  device dumps, apart from that BOLT #11 example key. No hardware wallets, no signing outside test
  vectors, no broadcast, no mainnet funds. (cyberkrill's root `trezor_address.json` and `test.psbt`
  are not copied.)

## 5. Licence: making dual-licence detection work

- **Root layout: `LICENSE-MIT` + `LICENSE-APACHE`, no root `LICENSE`**, exactly as cyberkrill.
  - GitHub's server reports this layout as GraphQL `licenseInfo.spdxId = Apache-2.0`. Checked
    2026-10-19 on `douglaz/cyberkrill`, `serde-rs/serde`, `rust-lang/cargo` and `rust-lang/rust`.
  - Reservoir's indexer reads exactly that field (`scripts/utils/repo.py`, `license_id(repo['licenseInfo'])`)
    and admits OSI-approved ids. So this layout passes, and Reservoir shows "Apache 2.0".
- **Rejected: one root `LICENSE` holding both texts.** licensee 9.18 (the library GitHub uses) returns
  NOASSERTION for it when run locally, and Reservoir drops NOASSERTION. This was not tested on GitHub's
  server, but the risk isn't worth taking. Note that the same local run also returned NOASSERTION for the
  two-file layout that GitHub's server detects, so the CLI is not a reliable stand-in for the server.
  Mixed layouts (`LICENSE` + `LICENSE-MIT`) are untested on the server.
- **Lakefiles:** `license := "MIT OR Apache-2.0"` (a valid SPDX expression) and
  `licenseFiles := #["LICENSE-MIT", "LICENSE-APACHE"]`. The default `#["LICENSE"]` would not exist.
  - Trade-off: Lake's own docstring (`Lake/Config/PackageConfig.lean` @ v4.35.0) says Reservoir
    "currently only supports single identifier SPDX expressions". Reservoir's package page shows the
    GitHub-detected id anyway.
  - So the accurate expression lives in the metadata while Reservoir displays "Apache 2.0", which
    understates the MIT option. `license := "Apache-2.0"` would match the display but misstate the
    grant. Default: the accurate expression; re-check at v1.
- **Subdirectory packages:** Phase 0 checks whether `licenseFiles` accepts `../../LICENSE-MIT`. If not,
  each package carries copies of both files (GitHub detection only reads the repo root).
- **Copied code** (lean4-hash, lean-miniscript) stays MIT: its original licence notice sits beside the
  copied files, never at the root.
- **Third-party material:**
  - Admitted in the tree, each with a provenance sidecar or header line (source URL, commit, path,
    licence), never the dual-licence header: MIT, BSD, ISC, CC0 or public domain, and CC-BY-4.0
    (attribution and a note of any changes, for example "extracted and reformatted", kept in the
    sidecar). Material offered under a choice that includes MIT (such as fedimint-lite's
    `MIT OR Apache-2.0`) is taken under MIT.
  - Kept out of the tree: Apache-2.0-only, share-alike (CC-BY-SA) and unlicensed material. Use a
    pinned non-flake input read at test time, or replace it with vectors we generate ourselves.
  - Copied code whose upstream file has no header gets a provenance comment (upstream repo, commit,
    path, "MIT") with the upstream MIT notice in a file beside it, never the dual-licence header.
- **Our headers:** `Copyright (c) 2026 lean-cyberkrill developers. Released under the MIT License or the
  Apache License 2.0, at your option; see LICENSE-MIT and LICENSE-APACHE.`

## 6. Defaults needing approval (approving the plan approves these)

1. SLIP-132 ships as a library function in `bitcoin` with vectors, but no CLI command (its only
   cyberkrill caller is the Trezor code).
2. bech32 proof scope:
   - The 4-error theorem is stated per variant (bech32 or bech32m) for data parts of at most 89
     characters, which covers every address (at most 90 characters); cross-variant acceptance is not
     covered (section 2).
   - BOLT11, LNURL and invites get round-trip plus checksum soundness, because BIP173 gives no 4-error
     guarantee past 89 data characters.
   - If the theorem needs Mathlib, it goes in `bitcoin-proofs`, with Mathlib as a pinned flake input.
     Mathlib's sandbox build time counts against the theorem's budget of 10 added minutes in
     `nix flake check`; over budget, the work session stops and reports.
   - If it proves out of reach, it comes back to the owner.
3. Proof hygiene: no `sorry`; no `native_decide` in library or proof modules; axioms limited to
   `propext`, `Classical.choice` and `Quot.sound`. lean4-hash already enforces this
   (`HashTest/Audit/AxiomGate.lean`). lean-miniscript's PSBT proof files are clean, but its
   `Psbt/CodecExamples.lean` (22) and `Psbt/FieldsExamples.lean` (3) use `native_decide`. Those vectors
   become `lake test` checks, and `native_decide` stays allowed in test-only files.
4. Network tests replay regtest RPC recordings and synthetic HTTPS response fixtures on a localhost
   stub only; no test needs a live `bitcoind`
   or the internet. (Amended on approval.) The Core RPC recordings are generated by a committed
   script that runs a throwaway regtest `bitcoind` from nix in a temporary directory, with wallets
   restored from published test mnemonics. Never record from the owner's own node or wallets.
5. `--descriptor` + `--bitcoin-dir` (the BDK route in cyberkrill) is rejected in v1 with a clear
   message, as is `--wallet-file` on the three PSBT commands.
6. Golden parity compares JSON values, not bytes; any exact-amount differences from cyberkrill's `f64`
   are documented.
7. Lakefile licence string `MIT OR Apache-2.0`; copyright holder "lean-cyberkrill developers".
8. Fall back to a hand-written CLI parser if lean4-cli has no v4.35-compatible release.

## 7. Post-v1: transaction equivalence with btc-verified (Phase 11)

Status: proposed on 2026-10-23 from an external analysis. The analysis and its verification notes
are in `docs/btc-verified-integration.md`, and "N1"–"N21" in this section refer to those notes.
Nothing here changes v1. Phase 11's beads are deferred, and they start after Phase 10b unless the
owner brings them forward. The owner answered all four questions at the end on 2026-10-23: 1
(toolchain route), 2 (licence footing), 3 (Mathlib and CI placement) and 4 (Core oracle).

**Goal.** Prove that `bitcoin`'s production transaction serialization agrees with an independently
formalized model, [`ProofOfKeags/btc-verified`](https://github.com/ProofOfKeags/btc-verified) @
`2fdeb40ca2b3f289896ed14a3340ad231cd16538` (Apache-2.0), and back the proof with differential
evidence against Bitcoin Core. `bitcoin` keeps its own codecs, PSBT, Base58, bech32, address and
amount modules. Nothing from btc-verified is copied into the tree.

**Non-goals.**
- Replacing `bitcoin`'s types or codecs. Only 11d may propose a type change, and the owner decides
  it.
- Consensus validity, Script execution or PSBT semantics. btc-verified has no Script interpreter
  and no PSBT code (N11).
- The bech32 4-error theorem. btc-verified has no bech32 code, so this phase does nothing for the
  deferred Phase 3b beads (`z3l`, `vxu`), and their new proof route is chosen separately.

**Constraints** (facts that hold whatever the owner decides):
- **Licence.** btc-verified and the Mathlib it requires are both Apache-2.0 only (N2, N3). Section
  5 keeps Apache-2.0-only material out of the tree, so neither is ever copied. Whether our own code
  may *depend* on them at build time was question 2. Its answer (below) allows it for the bridge and
  the btc-verified oracle, as pinned build-time dependencies.
- **Toolchain.** btc-verified pins Lean v4.30.0-rc2 and Mathlib `ee3a540`; this repo pins v4.35.0
  (N1). btc-verified's `lean-toolchain` has not changed since 2026-05-22. Lean cannot import
  modules built by another toolchain:
  - the bridge proofs (11c) need both on one toolchain;
  - the differential suite (11b) does not, because it compares separate processes.

  *Since question 1 was answered:* its answer (below) puts both on v4.35.0 through our own upgraded copy (11a, 2 of 2).
  So 11b's btc-verified oracle builds from that copy too, and CI carries no second Lean toolchain.
- **Mathlib.** Anything that imports btc-verified takes Mathlib with it (N3). Section 2 confines
  Mathlib to a separate `<pkg>-proofs` package. §6 #2 allowed Mathlib in `bitcoin-proofs` only if
  the 4-error theorem needed it, and counted Mathlib's sandbox build time inside `nix flake check`.
  The sandbox has no network, so Mathlib's prebuilt files (`lake exe cache get`) cannot be used
  there, and Mathlib's own documentation puts a build from source at several hours. *Since question
  3 was answered:* the Mathlib-dependent packages build in a separate CI job instead (below).
- **C code.** Section 1 allows C only in `secp256k1` and `http-curl`. btc-verified's own harness is
  C (N20).
- **Whole-repo check.** AGENTS.md requires every package to be in `lakePackages`, so that
  `nix flake check` covers it. Question 3's answer adds one named exception to that rule, for the
  Phase 11 Mathlib-dependent packages only.
- **Core's RPC body limit.** Core takes at most 32 MiB per HTTP request body (N21). So
  `decoderawtransaction` cannot see a container just over `MAX_SIZE` (N12); its hex alone is over
  64 MiB. `bitcoin-tx` reads hex from stdin with no such limit (N21).
- **No live node in tests.** §6 #4 says tests replay recordings and none needs a live `bitcoind`.
  A campaign generated from a recorded seed and budget by a pinned mutator is fixed before any test
  runs, so Core's answers to it can be recorded like any other §6 #4 recording. *Since question 4
  was answered:* they are, and §6 #4 holds unchanged.

**Package and CI** (question 3's answer):
- The bridge is its own package, `btc-verified-bridge` (a working name), not `bitcoin-proofs`. That
  keeps its Mathlib pin independent of the bech32 route's.
- The bridge and the 11b btc-verified oracle stay out of `lakePackages` and `nix flake check`. A
  second CI job, run on every PR beside the existing one, fetches Mathlib's prebuilt files with
  `lake exe cache get`, then builds and tests only those two packages: `lake build`, `lake test`,
  the no-`sorry` check, the axiom gate and the 11b suite. Every other package stays in
  `nix flake check`. For the merge gate, "CI green" means both jobs pass. This replaces §6 #2's
  in-check accounting for these two packages, and AGENTS.md names the exception.
- The job lands with the Phase 11 work, not before: 11b adds it with the oracle, and 11c (1 of 3)
  adds the bridge to it.

**Core oracle** (question 4's answer):
- Core is nixpkgs' `bitcoind` 31.1, from this repo's pinned nixpkgs, not `fc6923c`, the commit
  btc-verified pins. The transaction deserializer and `DecodeTx` are identical at the two (N21).
- A committed script, using the §6 #4 machinery, runs a throwaway regtest node in a temporary
  directory. For every input it records Core's answer to `decoderawtransaction <hex> true` and
  `<hex> false`: acceptance, `txid`, `hash` (the wtxid) and `size`. The inputs are the regression
  set plus a fixed, bounded campaign that a pinned mutator generates from a recorded seed and
  budget. The case over `MAX_SIZE` goes through `bitcoin-tx -` on stdin instead, and its rejection
  is recorded.
- The recording is committed and kept to a few MB. CI replays it, so neither CI job runs a node,
  builds Core or adds C. A digest over the inputs, every recorded answer, the mutator version and
  Core's version binds the recording. The recording script writes it to a separate committed
  manifest, never into the recording itself, and replay compares the recording's computed digest
  with it. So an answer edited by hand fails like a stale input, and a real re-record changes both
  files in review. A mismatch fails the suite and forces a re-record, and so does an input with no
  recorded answer; replay never invents a rejection.
- This gives up a fresh campaign on every run and coverage guidance. Core's transaction-check
  verdicts stay out of scope, as an 11b non-goal.
